部署方案

FundMesh 线上部署

部署至首尔 VPS，经 Cloudflare Tunnel 提供域名访问

目标机 141.164.53.169 与 polyorders 同机 镜像 453 MB 基线提交 dc3f9e7

01架构

两个关键决定及其理由

决定理由
用 Cloudflare Tunnel
而非 Caddy 反代		 该机 polyorders 的 Caddy 已绑定 0.0.0.0:80 与 :443，再起一个反代必然端口冲突。隧道是出站连接，不占端口、不需在源站签发和续期证书，也无需改动 polyorders 的任何配置。
在 VPS 上构建
而非拉 GHCR 镜像		 fundmesh 仓库为私有，私有包计入 GHCR 那 500 MB 配额（polyorders 已在使用）。而本项目镜像含 pandas / akshare，实测 453 MB，存不下几个版本。代价是构建负载落在 VPS 上，换来零配额依赖。

02资源评估

TimescaleDB 是 Postgres 的扩展，空载开销与普通 Postgres 相当（约 100–200 MB 内存）。真正的压力来自数据量，而不同阶段差着数量级：

阶段磁盘（压缩后）内存建议说明
本次上线（个人持仓 + 持有基金净值历史）< 100 MB512 MB几十笔流水、几万条净值
全市场基金日频（约 3000 万行）1–2 GB1 GB轻松
叠加股票日线（再约 3000 万行）2–4 GB2 GB仍然轻松
分钟级行情（几十亿行）20–40 GB4 GB+唯一真正的坎，届时再评估

本次上线新增占用合计约 1 GB：fundmesh 镜像 453 MB、TimescaleDB 镜像约 400 MB、初期数据不足 100 MB。

待核实：VPS 实际规格

该机已运行 polyorders 的 9 个容器（Next.js、scheduler、watcher、Caddy 等）。我没有该主机的可用凭据，无法实测规格 —— 本地仅有的 polyorders_deploy 密钥被 restrict,command= 限定为只能执行 polyorders 发布脚本，用它连接会触发一次 polyorders 生产部署，故未使用。

ssh root@141.164.53.169 'nproc; free -h; df -h /; docker system df'

把输出发我即可给出确切结论。按上表估算，只要磁盘余量 > 3 GB、内存余量 > 512 MB，本次上线即可安全进行。

04部署步骤

1

Cloudflare：创建隧道

控制台 → Zero Trust → Networks → Tunnels → Create a tunnel，类型选 Cloudflared，命名 fundmesh。

创建后选择 Docker 安装方式，复制命令中 --token 后的那一长串备用。

在 Public Hostnames 添加一条：

Subdomainfundmesh
Domainbluesignals.cc（与 polyorders 同域，或任意已托管域名）
TypeHTTP
URLweb:8000

web 是 compose 中的服务名 —— cloudflared 与它同处一个网络，按服务名解析即可。DNS 记录由隧道自动创建，无需手工添加。

2

GitHub：添加只读部署密钥

仓库为私有，VPS 需要凭据才能 clone。在 VPS 上生成一把专用密钥：

ssh-keygen -t ed25519 -f ~/.ssh/fundmesh_deploy -N ''
cat ~/.ssh/fundmesh_deploy.pub

把输出的公钥加到 仓库 Settings → Deploy keys，不要勾选写权限，并配置 SSH 使用它：

cat >> ~/.ssh/config <<'EOF'
Host github.com
  IdentityFile ~/.ssh/fundmesh_deploy
  IdentitiesOnly yes
EOF
3

VPS：首次部署

ssh root@141.164.53.169

mkdir -p /opt/fundmesh && cd /opt/fundmesh
git clone git@github.com:caiyin-bit/fundmesh.git app
cd app

cp .env.vps.example .env
vi .env          # 填 POSTGRES_PASSWORD 与 CF_TUNNEL_TOKEN

docker compose -f docker-compose.vps.yml up -d --build

首次构建约需数分钟（安装 pandas / akshare）。表结构由应用启动时的 init_db() 自动建立，没有单独的迁移步骤。

4

验证

cd /opt/fundmesh/app

# 三个服务均应 Up，db 为 healthy
docker compose -f docker-compose.vps.yml ps

# 首启日志：建表、同步交易日历、启用 TimescaleDB
docker compose -f docker-compose.vps.yml logs web | tail -30

# 确认 hypertable 已生效
docker compose -f docker-compose.vps.yml exec db \
  psql -U fundmesh -c "SELECT hypertable_name FROM timescaledb_information.hypertables;"

# 国内数据源从首尔的可达性与耗时
sh scripts/check-datasources.sh

随后浏览器打开 https://fundmesh.bluesignals.cc。

线上会自动启用 TimescaleDB

init_db() 会检测扩展是否可用，可用则把 nav_history 转为 hypertable 并挂上压缩策略。本地因 OrbStack 磁盘的块位图计数损坏（文件系统报 59.5 G 已用，实际仅 15.5 G）而未能启用，VPS 上为全新磁盘，不受影响。

05日常发布

ssh root@141.164.53.169 'cd /opt/fundmesh/app && sh scripts/vps-deploy.sh'

脚本依次执行 git pull → 构建 → 重启。构建失败时线上仍运行旧容器，失败的发布等于什么都没发生。

发布没有测试门禁

polyorders 的流水线以 pnpm test 把关，而 fundmesh 目前没有任何自动化测试，"失败的发布等于什么都没发生"这一性质仅覆盖构建错误，覆盖不到逻辑回归。

建议优先为核心计算补测试：XIRR（已有四组已知答案，可直接转为用例）、份额与成本推导、分红与拆分的顺序处理、估值加权。约半天工作量。

06备份

pgdata 卷是整套部署中唯一有状态的东西 —— 你的账目与行情历史。容器和镜像都可以随时重建，这个卷不能丢。

# 每日 03:00 导出，crontab -e
0 3 * * * cd /opt/fundmesh/app && docker compose -f docker-compose.vps.yml exec -T db \
  pg_dump -U fundmesh fundmesh | gzip > /opt/fundmesh/backup/$(date +\%F).sql.gz

两点提醒：设置保留策略，避免磁盘被历史备份塞满；只在同一台机器上留备份等于没有备份，机器没了备份一起没，需要异地副本（对象存储或另一台机器）。

07故障排查

现象排查方向
域名打不开，隧道显示 downdocker compose logs cloudflared。多为 token 填错或未重启；公开主机名的 URL 必须是 web:8000 而非 localhost:8000
502 / 无法连到源站确认 web 容器为 healthy；cloudflared 与 web 需在同一 compose 网络内
web 起不来，日志报连库失败确认 db 为 healthy；.env 中密码修改后需一并修改库内密码，否则连不上
页面能开但数据为空跑 scripts/check-datasources.sh，多为国内数据源从境外不可达或超时
构建时磁盘不足docker image prune -f；构建缓存可用 docker builder prune 清理

08已知限制

应用层没有任何认证

当前所有接口对外开放。上线后，任何知道域名的人都能查看你的持仓、成本与收益，并可调用 POST /api/transactions 修改账本。这是按你的决定「先部署、认证后续再加」执行的结果。

不改代码的过渡方案：在 Cloudflare Zero Trust → Access → Applications 为该主机名添加一条自托管应用策略，认证方式选邮箱一次性验证码。约五分钟配置完成，可在你补齐用户系统之前挡住全部陌生访问。

  • 数据源从首尔的可达性未实测。本地基线 10 项全通过，但境外访问国内接口的表现需在 VPS 上用 check-datasources.sh 确认。若耗时显著升高，需调大 HTTP 超时、延长大文件（基金全量列表 3.1 MB）的缓存 TTL、放宽盘中估值轮询间隔。
  • 无自动化测试，发布无逻辑门禁（见第 05 节）。
  • 净值同步依赖页面访问。目前仅在打开持仓页时回写最新净值，长期不访问会使 nav_history 出现空洞，收益曲线变稀疏（有前值填充，不会算错，但精度下降）。后续可加一个夜间同步任务。
  • 代理估值缺少设置入口。assets.proxy_code 字段与逻辑均已就绪，但没有界面可设置；当前一律走重仓股加权（覆盖率 47%–95%，界面已标注）。
